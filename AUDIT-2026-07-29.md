## HIGH

### 1. Generated-flora organs render with black albedo — `vertexColors: true` on geometry with no `color` attribute

`src/generated-flora/renderers.js:51-60` builds materials with `vertexColors: true`
(nearly every organ plan in `archetypes.js` opts in: canopy leaf, cap cap/lobe/spot/
pendant, bell bloom/pulse/leaf, frond, pad, reed blade/plume, cover blade, coral tip,
spire bud/ring — only cap filament and pad spine don't). But the organ builders in
`src/generated-flora/organs.js` (`buildCap`, `buildBell`, `buildBlade`, `buildFrond`,
`buildPad`, `buildBulb`, `buildBerry`, `buildTendril`) **never emit a `color`
attribute** — only `buildStemGeometry` does (`renderers.js:164`).

Mechanism, verified in the vendored three 0.185.1:

- `WebGLProgram.js:567` defines `USE_COLOR` from `material.vertexColors` alone.
- Base `Material` in r185 has **no** `defaultAttributeValues` (grep-confirmed;
  only `ShaderMaterial.js:238` carries it).
- `WebGLBindingStates.js:331-340` only substitutes missing attributes for
  `instanceMatrix` / `instanceColor`.

So the unbound `color` attribute reads GL's generic default `(0,0,0)` → `vColor`
black → `diffuseColor *= vColor` black. Per-instance tinting (`writeColors`,
`generated-flora/index.js:293-314`) cannot rescue it: `vColor *= color` runs
**before** `vColor *= instanceColor`. Additionally rasterized in headless Chrome
against the vendored three: black pixels; red `instanceColor` still black.

Net effect: every leaf, cap, bloom, frond, pad, bud renders as a black silhouette
with emissive-only glow; stems escape (baked attribute). The donor code follows
the rule everywhere (`src/flora/trees.js:73` pairs the flag with
`setAttribute("color", …)` at `:97`) — the new generator broke it. The
`screenshots/` dir contains only donor-world shots (Jul 4), so this shipped unseen.

**One-glance confirmation:** open `localhost:2001`, compare leaves vs. stems.
**Fix (one line, either direction):** drop `vertexColors` on organ materials
(instance tinting works alone), or bake a white `color` attribute into organ
geometries. No test rasterizes, so add one if a cheap harness exists.

### 2. Failed in-place plant regrow leaks a compiled species, once per failure

Found independently by three auditors.

`src/living-world/runtime.js:1136-1138` registers the species, provider, and
`species.batchRoot` into the scene **before** placement is attempted. If all 24
ring candidates fail, `addLivingFlora` returns null and the function throws at
`runtime.js:1188-1190` with none of that rolled back. The species-GC in
`removeLivingFlora` (`runtime.js:924-931`) can never reach it — no `flora` entry
exists for it. This is exactly the path `rebuildPlant` walks
(`src/ui/observatory.js:1335-1347`): first attempt with `at` throws ("a taller
hero needs more room"), the catch retries without `at` — so one failed slider
drag orphans one or two compiled species (geometry, materials, batch roots) for
the rest of the session. `disposeLivingWorld` eventually gets them, so it's
session-scoped. The comment at `runtime.js:920-923` shows this leak class was
understood and fixed **only on the success path**.

The kin twin has the inverse problem: `rebuildKin` (`observatory.js:1310-1325`)
does `facade.dispose()` then `introduceLivingFauna(...)` with **no try/catch**
(unlike the plant branch). A throw deletes the animal permanently, escapes the
debounce timer uncaught, and strands the card pointing at a disposed facade —
every later commit no-ops silently.

**Fix:** roll back registration/scene-parenting on the throw path (or register
only after a successful placement); wrap `rebuildKin` like the plant branch.

## MEDIUM

### 3. Genome card survives world regen — kin edits silently no-op forever, plant edits teleport into the new world

The `world-ready` handler (`observatory.js:1196-1204`) never closes the card or
clears `cardSubject`, which holds old-runtime facade/flora references.

- Kin path: `rebuildKin` searches the **new** `runtime.fauna` for the old facade,
  finds nothing, returns null — the card stays fully alive (nibs move, marginalia
  appears, hash pulses) while changing nothing. It lies to the player.
- Plant path (worse): `rebuildPlant` reads `flora.instance.root` off the old
  flora object, `removeLivingFlora` returns false, and it **plants the edited
  draft into the new world** at the old coordinates — an uninvited plant from a
  closed chapter.

Reachable because `show()` never moves focus into the card, so window-level
regen shortcuts (`input.js:307+`) stay live behind the scrim; any future
async/timed regen hits it too.
**Fix:** close the card (or clear `cardSubject`) on `world-ready`.

### 4. Perched flier is shoved off its perch by the host plant's own obstacle

Hero obstacles are trunk-centered circles (`runtime.js:697-713`); every hero's
`perch` affordance sits at plant-local `[0, height, 0]` — directly above the
obstacle centre (`src/generated-flora/renderers.js:177-182`).
`stepLivingFauna` applies `resolveAgainstObstacles` to perched fliers
(`runtime.js:1524-1527`), so the frame it "lands" it is pushed horizontally out
to `r + body` (~0.8–1.1 units) and floats beside the plant for the whole 7–12s
dwell, while the dwell branch pins its target back to the perch point
(`kin-goals.js:329`). The donor solved exactly this with `skipX/skipZ`
(`src/fauna/shared.js:332-335`); the port dropped it. `reachableRadius`
(`kin-goals.js:211-224`) masks it (standoff counts as arrival), so no test sees
it. On a canopy hero the foliage hides it; **on a spire the flier visibly hovers
~0.8 units off a thin stalk** — the headline "sitting on the crown" moment
broken for one of three hero archetypes. `updateFlight`'s doc comment
(`runtime.js:1436-1439`) describes behaviour the code does not deliver.

### 5. Flier `forage` is unsatisfiable on ~1/3 of worlds, and goal choice has no fallback

`ROLE_DRAW.mid = 2` drawn from three mid families (`roster.js:179, 415-425`), so
one world in three lacks `pulsebell`. Only the bell archetype advertises
`nectar`/`pollen` (`archetypes.js:454` — verified across all eight archetypes),
and the flier's forage need answers only `["nectar", "pollen"]`
(`kin-goals.js:66-71`). No bell → need pins at 1.0 forever. Worse,
`chooseKinGoal` (`kin-goals.js:233-244`) evaluates only the single strongest
need; when forage is strongest it scans, finds nothing, returns null instead of
falling back to the second-strongest — the flier dithers goalless ~20s after
each perch visit. The suite only exercises seed `0x1e`, whose roster drew a
bell, so the gap is invisible to tests. Same bug class HANDOFF says was fixed
for walkers.

### 6. `variation scale range reordered` repair note is filed where no row can show it

`repairTarget` (`genome-draft.js:93-104`) accepts section paths and files the
note under `"variation"`, but `syncRow` (`genome-card.js:176`) only looks up
field paths — the note vanishes (and never reaches `general`). Verified live:
drag `variation.scaleMin` (max 1.1) past `scaleMax` (min 0.9) → the held slider
silently swaps 1.1→0.9, the *other* slider lights up as "moved", and the single
explanatory note is invisible. Breaks the module's load-bearing claim
(`genome-draft.js:14-17`) that every note "can be shown next to the field the
player just moved without lying". `tests/genome-draft.test.mjs:162` pins the
misrouting as correct — fix the routing AND the pin.

### 7. The determinism gate tests a copy of the mechanism, and never exercises the default shipping mode

- `tests/determinism-seed.test.mjs:116-153` defines its own
  `installSeededRandom`/`restoreRandom`/`yieldIfNeeded` closures that "mimic"
  `src/world.js:342-349`. Drop the restore-before-await in the real code and
  Layer 1 stays green. Layer 2 (`:215-263`) spawns node processes with no
  concurrent `Math.random` consumer — equally blind. In the browser, `animate()`
  interleaves 564 `Math.random` calls across 45 files with generation yields;
  a dropped restore breaks determinism in production only.
- The Layer-2 probe stubs `window.location.search = ''` → living-world flags
  all false → species compilation and batch building run **zero times** under
  the gate. But `main.js:72-93` (`activateDefaultLivingWorld`) now auto-injects
  `?livingWorld=1` when no explicit mode param exists — the default shipping
  mode is exactly what the gate skips.

The seeded-window **implementation** is genuinely correct (namespaced
`hashSeed` streams, try/finally around every await, run-id supersession — all
verified). The **enforcement** is the hole.
**Fix:** test the real `generateWorld` with a hostile concurrent `Math.random`
consumer; run the byte-equality probe with living-world flags on.

### 8. The three hottest shader string-patches have no anchor verification — and the project owns `replaceOrWarn` for exactly this

`src/generated-flora/batch.js:199-201` (`applyTouchBend`), `src/util.js:80-142`
(`applyWindSway`), `src/generated-fauna/shell.js:511-538` (`injectShell`) all
patch with raw `String.replace`. `src/util.js:170-176` documents why that's
unacceptable, and grass/water/decals/pbr all use `replaceOrWarn` — the new
flora/fauna code doesn't. A three upgrade renaming `project_vertex` /
`begin_vertex` / `beginnormal_vertex` silently deletes the touch bend, wind
sway, or the entire SDF shell with a successful compile. The test that looks
like it guards this (`generated-flora-renderer.test.mjs:188-208`) patches a
**mock** shader string containing the anchors by construction — CI stays green
through a real anchor break. Secondary: `TOUCH_PROJECT_VERTEX` (`batch.js:128-172`)
re-implements `project_vertex` but drops the `USE_BATCHING` branch r185 carries.
